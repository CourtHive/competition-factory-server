# Roles & Permissions

The server uses a two-tier authorization model:

- **Global capability roles** live in the `users.roles` JSONB array, travel in the JWT, and gate *whether a user may call an endpoint at all* via the `@Roles([...])` decorator (enforced by `RolesGuard` for HTTP and `SocketGuard` for WebSocket handlers).
- **Provider-scoped roles** live in `user_providers.provider_role`, are **not** in the JWT, and answer *what a user may do within a specific provider's scope*. They are resolved per request from the user's provider associations (the `UserContext`).

The canonical definitions are in `src/common/constants/roles.ts`.

These are valid in the JWT and via `@Roles(...)`. `VALID_GLOBAL_ROLES` = `[superadmin, developer, generate, client, score, provisioner]`.

Beyond the role gate, `executionQueue` applies a per-tournament authorization gate (`canMutateTournament` plus the owning provider's mutation-permission map); `superadmin` bypasses both.

## Provider Scoping

Users are associated with one or more providers (organisations) via `user_providers`. When logged in:

- A `superadmin` can manage **all providers and users** and is exempt from scoping.
- A `PROVIDER_ADMIN` (provider-scoped role) sees and manages **all tournaments in that provider**.
- A `DIRECTOR` (provider-scoped role) sees only tournaments they **own or were assigned**.

View/mutate scoping is gated by the `ENABLE_TOURNAMENT_ACCESS_SCOPING` flag (`isTournamentAccessScopingEnabled`); delete authorization is always provider-bound regardless of the flag.

## Audience-Aware Authentication

JWTs also carry an `aud` (audience) claim. `AuthGuard` (HTTP) and `SocketGuard` (WebSocket) admit a token only when its `aud` overlaps the route/gateway's required audiences, declared via the `@Audience([...])` decorator.

- Audience claims: `admin` | `hiveid` | `score` (defined in `audience.decorator.ts`; the tracker-token service also mints a `provider` audience).
- Absent `@Audience(...)` defaults to `['admin']`; legacy tokens with no `aud` claim are treated as `admin`, so existing sessions keep working.
- Example: `POST /factory/score` declares `@Audience(['admin', 'score'])` so both TMX-user tokens and score-relay service tokens are accepted.

## Managing Roles

```bash
# Set roles for a user
node src/scripts/admin-user.mjs set-roles \
  --email user@example.com \
  --roles developer,client,score

# Demote to client-only
node src/scripts/admin-user.mjs set-roles \
  --email user@example.com \
  --roles client
```

`admin-user.mjs` validates against `[superadmin, admin, developer, client, score, generate]` (note `admin` is still accepted for back-compat), and its `create` command provisions a superadmin (`roles: [superadmin, admin, client]`).

## JWT Token Structure

On login the server signs a short-lived access token (`buildSessionPayload` + `signAccessToken`) roughly shaped as:

```json
{
  "email": "user@example.com",
  "roles": ["client"],
  "permissions": [],
  "providerId": "uuid-of-home-provider",
  "providerIds": ["uuid-a", "uuid-b"],
  "providerAssociations": [
    { "providerId": "uuid-a", "providerRole": "PROVIDER_ADMIN" }
  ],
  "lastSelectedProviderId": "uuid-a",
  "aud": "admin"
}
```

The access token TTL is `ACCESS_TOKEN_TTL` (currently `4h`). A separate rotating **refresh token** is issued alongside it and can be exchanged for a fresh access token via the refresh flow. Provider-scoped roles (`PROVIDER_ADMIN` / `DIRECTOR`) are **not** in the token — they are resolved per request from `providerAssociations`.
