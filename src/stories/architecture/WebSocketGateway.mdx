# WebSocket Gateway

The server uses Socket.IO for real-time bidirectional communication with TMX clients. All tournament mutations, broadcasts, and notifications flow through the WebSocket gateway.

## Namespace

All TMX communication uses the `/tmx` Socket.IO namespace, declared on `TmxGateway` via `@WebSocketGateway({ cors: { origin: resolveCorsOrigins(process.env.CFS_CORS_ORIGINS) }, namespace: 'tmx' })`. The origin is allowlist-driven: unset or `*` accepts all origins (default), while `CFS_CORS_ORIGINS` (comma-separated) locks it to known origins in production. See `src/common/cors.ts`.

```typescript
// Client connection — the JWT is supplied via the auth callback so it
// is re-sent on every reconnect (see Authentication below)
const socket = io('http://localhost:8383/tmx', {
  auth: (cb) => cb({ token: currentAccessToken }),
});
```

## Message Types

Each handler is a `@SubscribeMessage(...)` method on `TmxGateway`, guarded by `SocketGuard` and (except `test`) a `@Roles([...])` decorator.

## Authentication

There is **no** `authenticate` message. `SocketGuard` (applied to `TmxGateway` via `@UseGuards(SocketGuard)`) authenticates and authorizes every guarded message:

1. The client supplies its JWT through the Socket.IO `auth.token` handshake field (preferred — it is re-sent on every reconnect, so it survives token rotation) or, as a fallback, an `Authorization: Bearer` header.
2. `SocketGuard` verifies the JWT with `JWT_SECRET`.
3. It runs an **audience** check: the token's `aud` claim must overlap the gateway's required audiences. Absent `@Audience(...)` defaults to `['admin']`, and legacy tokens with no `aud` claim are treated as `admin`.
4. It enforces the handler's `@Roles([...])` (most handlers require `CLIENT` or `SUPER_ADMIN`) and stores the verified user on `client.data.user` for downstream handlers.

On failure the guard emits an `exception` event and rejects the message. `executionQueue` applies an additional per-tournament authorization gate (`canMutateTournament` + the owning provider's mutation-permission map) before the mutation runs.

## Mutation Acknowledgement

Each `executionQueue` request includes an `ackId`. The server (`tmxMessages.executionQueue`) responds with an `ack` event:

```json
// success
{ "ackId": "original-request-id", "success": true }

// error (optional context/info/stack/tournamentIds included when present)
{ "ackId": "original-request-id", "error": "…", "tournamentIds": ["…"] }
```

The client waits for this `ack` before applying mutations locally, ensuring server-client consistency.

## Per-Request State Isolation

The gateway serves many concurrent sockets from one Node.js process. Each `executionQueue` runs against its own factory-engine state, isolated via Node.js `async_hooks` (`asyncGlobalState`), while `withTournamentLock` serializes requests that touch the same tournament. See [Mutation Flow](?path=/docs/architecture-mutation-flow--docs) for details.

## Broadcasting

When a tournament is modified — whether by a TMX client via Socket.IO or an external app via the REST API — the server broadcasts changes through two channels:

1. **`/tmx` namespace** — full methods array sent to other authenticated TMX clients in the tournament room (sender excluded)
2. **`/public` namespace** — sanitized score/status payloads sent to all public viewers (no authentication required)

Broadcasting is handled by `TournamentBroadcastService`, a shared service used by both `TmxGateway` and `FactoryController`. See [Public Notifications](?path=/docs/architecture-public-notifications--docs) for details on consuming public updates from external applications.
