# End-to-End Mutation Flow

All tournament data mutations follow a single path through client, server, and factory engine.

## Flow Diagram

```
User Action (TMX client)
  → mutationRequest()
    → emitTmx('executionQueue', payload)
      → Socket.IO → /tmx namespace
        → TmxGateway.messageHandler()
          → tmxMessages.executionQueue()
            → executionQueue()
              → withTournamentLock()
              → fetchTournamentRecords()
              → mutationEngine.executionQueue(methods)
              → saveTournamentRecords()
            → client.emit('ack')
      → On ack: client runs same mutations locally
        → saves to IndexedDB
```

## Message Format

```json
{
  "type": "executionQueue",
  "payload": {
    "methods": [
      { "method": "addEvent", "params": { "..." } },
      { "method": "addDrawDefinition", "params": { "..." } }
    ],
    "tournamentIds": ["tournament-uuid"],
    "rollbackOnError": true,
    "ackId": "unique-request-id"
  }
}
```

## Server-First Execution

With `serverFirst: true` (default), the flow is:

1. **Client** sends mutation methods to the server via Socket.IO (`executionQueue` message)
2. **Server gateway** (`TmxGateway.messageHandler`) authorizes the request per-tournament — `canMutateTournament` access plus the owning provider's mutation-permission map — and stamps the JWT-verified identity onto the payload
3. **Server** (`executionQueue`) acquires the per-tournament lock (`withTournamentLock`)
4. **Server** fetches tournament records from storage into the request's isolated factory-engine state
5. **Server** executes all methods via `mutationEngine.executionQueue(methods, rollbackOnError)`
6. **Server** saves updated records to storage (then flushes deferred cache keys and records the audit entry, still inside the lock)
7. **Server** (`tmxMessages.executionQueue`) sends `ack` back to the originating client
8. **Server gateway** broadcasts the approved methods to other `/tmx` clients in the tournament room and sanitized notices to `/public` viewers
9. **Client** receives `ack`, applies the same mutations locally via the factory engine
10. **Client** saves to IndexedDB

The `ack` is emitted from `tmxMessages.executionQueue` (see `client.emit('ack', response)`); the broadcast then happens back in `TmxGateway.messageHandler` once the handler returns success.

## Per-Request State Isolation

The server processes many concurrent requests through a single Node.js process, so the factory engine cannot hold mutable state on a shared singleton. Instead, each request gets its own factory-engine state via Node.js `async_hooks`:

- `getMutationEngine` builds an `asyncEngine()` instance and wires the factory's state provider to `asyncGlobalState` (`globalState.setStateProvider(asyncGlobalState)`).
- `asyncGlobalState` registers an `async_hooks` `createHook` and keys per-context state (`tournamentRecords`, `subscriptions`, `notices`, `methods`, `modified`) by `executionAsyncId()`. The `init` hook propagates state to child async contexts; `destroy` cleans it up.
- Because state is scoped to the async execution context, two concurrent `executionQueue` requests never see each other's `setState(...)` / notices — no cross-request contamination.
- The same isolation lets `resolveMatchUpReferences` safely use `tournamentEngineAsync.setState(...).findMatchUp(...)` to backfill `drawId`/`eventId` on `setMatchUpStatus` methods that carry only a `matchUpId`.

Per-request state isolation and the per-tournament mutex are complementary: `async_hooks` keeps concurrent requests' engine state separate, while `withTournamentLock` serializes requests that target the *same* tournament so their read-modify-write cycles cannot interleave.

## REST API Mutations

External applications can submit mutations via `POST /factory` (authenticated with JWT). These mutations follow the same execution path (lock, fetch, execute, save) and now also broadcast to connected TMX clients and public viewers:

```
External App → POST /factory { methods, tournamentIds }
  → FactoryController.executionQueue()
    → server executes and saves
    → broadcastService.broadcastMutation()     → /tmx clients notified
    → broadcastService.broadcastPublicNotices() → /public viewers notified
  ← HTTP 200 { success, results }
```

See [Public Notifications](?path=/docs/architecture-public-notifications--docs) for details on consuming updates from the `/public` namespace.

## Offline / Local-First Mode

When disconnected from the server (or no provider configured):

1. **Client** executes mutations directly via local factory engine
2. **Client** saves to IndexedDB
3. Mutations queue for server sync when reconnected

## Tournament Locking

The server uses per-tournament mutexes to prevent concurrent modifications:

- Keys are sorted before acquisition to prevent deadlocks
- 30-second timeout prevents stuck locks
- Lock granularity is per-tournament, not global — different tournaments can be modified concurrently

## Error Handling

- `rollbackOnError: true` — if any method fails, all changes are reverted
- Error response includes the failed method name and error details
- Client shows toast notification on mutation failure
