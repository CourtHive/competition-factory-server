# Response Caching

Read endpoints on `FactoryController` are cached for **3 minutes** so that polling clients — mobile, the
public viewer, automated dashboards — do not recompute the same payload on every request. Writes evict
what they changed.

The interesting parts are the two that are easy to get wrong: **how much a write invalidates**, and
**when a write is allowed to re-seed**.

## Cache keys

Every cached read is stored under a `<prefix>|<tournamentId>[|<...>]` key. Segment `[1]` is always the
tournament id — that is what makes per-tournament invalidation possible.

| Key                    | Endpoint                                                   | Scope                            |
| ---------------------- | ---------------------------------------------------------- | -------------------------------- |
| `gti\|<tid>`           | `GET /factory/tournamentinfo/:tid`                         | tournament                       |
| `gti\|<tid>\|<flags>`  | `POST /factory/tournamentinfo`                             | tournament, per flag combination |
| `ged\|<tid>\|<eid>`    | `POST /factory/eventdata`                                  | **one event**                    |
| `gdd\|<tid>\|<did>`    | `POST /factory/drawdata`                                   | **one draw**                     |
| `gdd\|<tid>\|<did>\|s` | `POST /factory/drawdata` with `structuresProfile: 'STUBS'` | **one draw**, thin               |
| `gsd\|<tid>\|<sid>`    | `POST /factory/structuredata`                              | **one structure**                |
| `gtm\|<tid>`           | `POST /factory/scheduledmatchups`                          | tournament                       |
| `gtp\|<tid>`           | `POST /factory/participants`                               | tournament                       |
| `gmr\|<tid>`           | `POST /factory/matchups`                                   | tournament                       |
| `gac\|<tid>`           | `GET /factory/assistant-context/:tid`                      | tournament                       |

`cacheFx(key, fx, params)` is the single wrapper: on a hit it returns the stored value stamped
`_cached: true`; on a miss it calls `fx`, and stores the result only when there is no `error`.

Because `cache-manager` has no prefix-delete primitive, the controller keeps a **side-table** of every key
it has issued per tournament. That table is capped at 200 keys per tournament with FIFO eviction, so a
client polling many flag-variant combinations cannot grow it without bound. A key evicted from the
_tracking_ set is not iterate-evicted on the next mutation; it ages out via the TTL instead.

## Invalidation happens at two layers

### Layer 1 — notice handlers (`getMutationEngine.ts`)

Factory notices fire during the mutation. Handlers evict what they can attribute:

- `clearCache(tournamentId)` evicts the **tournament-scoped** shapes — `gti|`, `gtm|`, `gac|`, `gtp|`,
  `gmr|`. These aggregate across events, so any write can change them.
- `evictEventData` / `evictDrawData` / `evictStructureData` evict **one** entity key each and record
  that a targeted eviction happened. `evictDrawData` evicts **both** `structuresProfile` variants —
  they are separate documents, and sparing the thin one would serve a stale structure list.

`clearCache` deliberately does **not** touch per-entity keys — those belong to the topics that know
which entity changed.

> **Where the identity comes from — and where it stops.** As of factory **6.27.0** `MODIFY_MATCHUP`
> declares `eventId`, `drawId` and `structureId` on its envelope. **`structureId` is declared but not
> populated:** 57 of factory's 61 `modifyMatchUpNotice` call sites never pass one, every score path
> included. So the structure tier currently cannot be targeted from a score, and falls back to a
> wholesale sweep (see _Unattributable changes_ below). `drawId` and `eventId` are populated. Before that it was only
> `{ matchUp, tournamentId, context }`, and a score had to evict via `MODIFY_DRAW_DEFINITION` — a
> sibling topic that happened to fire on the same mutation. The notice-identity work
> (`Mentat/planning/FACTORY_NOTICE_IDENTITY_AUDIT.md`) is what makes structure-grain eviction possible
> at all: without `structureId` on the topic that describes a score, there is nothing to evict against.

### Layer 2 — the controller (`invalidateTournamentCache`)

After a successful write the controller sweeps the side-table. It **narrows** when the mutation reported
targeted evictions: per-**entity** keys (`ged|`, `gdd|`, `gsd|`) not named in that list are **spared**,
while every tournament-scoped key still goes — those aggregate across entities, so any write can move
them.

**Fail-safe, one:** narrowing happens only when at least one targeted eviction was reported. An empty
list means no notice carried an eventId, so the controller falls back to the original tournament-wide
sweep. _Invalidate less_ must never silently become _serve stale_.

**Fail-safe, two — unattributable changes.** The first fail-safe is not enough on its own, and the gap
is subtle enough that it shipped once. A handler that sees a change it _cannot name_ — a
`MODIFY_MATCHUP` with no `structureId` — used to evict nothing and say nothing. To the controller that
is indistinguishable from _nothing changed at that grain_, so the key was **spared** and the tier served
stale data for the full TTL, even though the other tiers narrowed correctly and the request looked
healthy.

So the eviction helpers now report the prefixes they could not attribute, via
`FactoryRequestContext.unnarrowablePrefixes`, and the controller sweeps those tiers wholesale. Coarse,
but never stale.

| Handler sees                     | Records           | Controller                          |
| -------------------------------- | ----------------- | ----------------------------------- |
| change **with** the entity id    | the exact key     | spares every other key in that tier |
| change **without** the entity id | the tier's prefix | sweeps that whole tier              |
| no change at that grain          | nothing           | spares the tier                     |

The middle row is the one that did not exist before.

Spared keys are written back into the side-table so a later write can still find and evict them.

#### Why this matters

Measured on a Grand-Slam-shaped tournament (5 events, 635 matchUps — see
`Mentat/tools/slam-scale-bench`):

|                                                |             |
| ---------------------------------------------- | ----------- |
| Cached event payloads, all 5 events            | **3.26 MB** |
| The entire `tournamentRecord` they derive from | 0.82 MB     |
| `getEventData` for all 5 events                | ~92 ms      |

`getEventData` denormalizes participants into every matchUp side, so the cached payload is **four times
larger than the record it is built from**. Before narrowing, one score discarded all of it — including
four events that had not changed.

## Decomposed tiers — event → draw → structure

`POST /factory/eventdata` returns every draw with every structure. A client that wants one bracket pays
for all of them, and any change anywhere discards the lot. The `drawdata` and `structuredata` endpoints
let a client fetch what it is actually rendering.

**Be precise about what this buys, because it is not what it looks like.** The narrower endpoints do
**not** skip factory compute — measured, every draw is a single structure group, so `getStructureData`
assembles the same work `getDrawData` does. The gain is entirely in the other two dimensions:

|                           | Event tier             | Draw tier | Structure tier |
| ------------------------- | ---------------------- | --------- | -------------- |
| Response size             | whole event            | one draw  | one structure  |
| Invalidation blast radius | all draws in the event | one draw  | one structure  |
| Factory compute           | —                      | —         | **the same**   |

So the tiers are worth having for **payload** and **eviction granularity**, not for CPU. A score in one
structure now leaves its siblings' cached payloads intact; before, it discarded the entire event.

`structuresProfile: 'STUBS'` on `drawdata` returns draw metadata without structures — a draw list, for
navigation, at a fraction of the size. It is a distinct cache key, never a variant of the same one.

**Additive only.** `eventdata` is unchanged in shape and default behaviour. ClubSpark runs the existing
pattern at scale for USTA and ITA; these are new routes alongside it, not a migration.

## `warmCache` — opt-in re-seeding

A write can ask CFS to re-seed the per-event payloads it just evicted:

```json
POST /factory
{
  "tournamentIds": ["<tid>"],
  "methods": [{ "method": "publishEvent", "params": { "eventId": "<eid>" } }],
  "warmCache": true
}
```

**Default is `false`, and that default is deliberate.** Building the payload is exactly the cost the
normal path avoids. Turn it on when a reader is imminent; leave it off otherwise.

| Publish shape                           | `warmCache` | Why                                     |
| --------------------------------------- | ----------- | --------------------------------------- |
| Draw released, crowd about to look      | **on**      | the miss is user-visible                |
| Draft / administrative / bulk republish | **off**     | no reader is coming; the build is waste |

Mechanics, and the reasons behind them:

- **Re-seeds exactly the keys that were evicted this request** — the same list the narrowing uses.
- **Seeds through `cacheFx`**, never a hand-built object, so the seeded and naturally-cached shapes
  cannot drift. This is a real failure mode, not a hypothetical: the cached value is the full
  `{ success, eventData, participants }` result, and seeding the notice's inner `eventData` alone would
  serve a participants-less shape that **blanks every bracket side to TBD for the full TTL**.
- **Runs strictly after invalidation** — seeding first would only feed the sweep.
- **Awaited, not fire-and-forget.** The caller opted in because a reader is imminent; returning before
  the cache is populated would race that reader, and a detached promise would swallow errors.

The flag lives on the executionQueue payload rather than on `publishEvent` params, so the **factory never
sees it** — caching is a server concern and this keeps it there.

> **Client status.** `warmCache` is available on the API; TMX does not set it yet. Until a client passes
> it, behaviour is unchanged.

## WebSocket vs HTTP

Both paths run the layer-1 handlers. Only the HTTP controller keeps the side-table, so **flag-variant**
`gti|<tid>|<flags>` keys are evicted on the HTTP path but not by `clearCache`. A WS-driven mutation
therefore leaves flag-variant tournamentInfo reads stale until the TTL elapses — acceptable, because the
live broadcast already notifies interactive clients, and consumers needing consistency should read the
no-flags route.

## Adding a cached endpoint

1. Build a key shaped `<prefix>|<tournamentId>[|<...>]` — segment `[1]` **must** be the tournament id.
2. Read through `cacheFx`, which handles hit/miss, the TTL and side-table tracking.
3. Decide the scope. Tournament-wide? Add it to `clearCache`. Narrower than that? Evict it from the
   topic handler that knows the identifying id, and record the eviction so the controller can spare it.
4. **Add the prefix to `PER_ENTITY_PREFIXES`.** A per-entity key not listed there is swept on every
   write — correct, but it throws away the granularity that was the reason for adding the endpoint.
5. **Make the evicting helper report when it cannot attribute a change**, rather than returning early.
   A silent skip reads as "nothing changed" and the key gets spared. This is the failure that shipped
   in #906 and was caught in review, not by CI.
